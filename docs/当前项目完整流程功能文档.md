## 2. 项目定位

`astrbot_plugin_engram` 是一个面向 AstrBot 的长期记忆增强插件。它不是简单地“保存聊天记录”，而是把对话处理成三层能力：

1. **原始消息层**：完整保存用户与助手的原文对话，作为唯一事实源。
2. **长期记忆层**：将原始消息异步总结为可检索、可回溯的长期记忆索引。
3. **用户画像层**：从长期记忆中进一步抽取稳定偏好、属性、关系与统计信息。

这样，插件既能让模型“记得发生过什么”，也能让模型“知道这个人是什么样的人”。

## 3. 整体架构

### 3.1 核心模块

当前项目可以分为以下几个核心层次：

| 模块 | 作用 |
|---|---|
| `main.py / EngramPlugin` | 插件入口、事件路由、组件装配、WebUI/调度器启动 |
| `MemoryFacade` | 记忆系统统一门面，协调记忆与画像 |
| `MemoryManager` | 原始消息记录、长期记忆归档、检索、删除、撤销、导出、向量补偿 |
| `DatabaseManager` | SQLite 持久化层，负责表模型、查询与自动迁移 |
| `ProfileManager` | 用户画像读写、每日更新、快照与回滚 |
| `MemoryScheduler` | 周期性归档、折叠、画像更新、维护任务 |
| `IntentClassifier` | 判断用户消息是否值得触发长期记忆检索 |
| `LLMContextInjector` | 将画像和记忆回溯块注入到 LLM prompt |
| `ExportHandler` | 导出原始消息为微调数据 |
| `EngramWebServer` | WebUI 后端接口 |
| `ProfileRenderer` | 将画像渲染为手账风格图片 |

### 3.2 总体运行关系

系统运行时形成如下关系：

- **消息进入**：AstrBot 触发私聊/群聊事件。
- **原文落库**：`MemoryManager` 先保存原始消息。
- **异步归档**：`MemoryScheduler` 定时检查未归档消息并生成长期记忆。
- **请求前检索**：在 LLM 正式回答前，插件根据意图决定是否检索长期记忆。
- **画像注入**：用户画像与长期记忆共同注入 prompt。
- **后台管理**：WebUI 提供查询、统计、浏览、删除等能力。

## 4. 系统启动流程

### 4.1 启动目标

插件加载时，会完成以下初始化：

- 读取配置并应用预设
- 创建私聊记忆与画像主链路
- 创建后台调度器
- 按配置决定是否启动 WebUI

- `self.logic`：`MemoryFacade`

- `self.profile_renderer`
- `self._scheduler`
- `self._webui_server`（若启用）

系统启动完成后，可持续提供：

1. 私聊原始消息记录
2. 群聊原始消息记录（若启用）
3. 请求前长期记忆检索与注入
4. 定时长期记忆归档
5. 定时用户画像更新
6. 记忆折叠与维护任务
7. WebUI 控制台与 API（若启用）

## 5. 数据模型与存储结构

### 5.1 私聊存储

默认私聊数据保存在插件数据目录下：

- SQLite：`engram_memories.db`
- ChromaDB：`engram_chroma/`
- Persona JSON：`engram_personas/{user_id}.json`
- Persona History：`engram_personas/history/{user_id}.json`
- Export：`exports/`

### 5.2 群聊存储

群聊链路独立使用：

- SQLite：`engram_memories_group.db`
- ChromaDB：`engram_chroma_group/`

### 5.3 核心表

#### `RawMemory`

原始消息表，保存所有进入记忆系统的原文消息，常见字段包括：

- `uuid`
- `session_id`
- `user_id`
- `user_name`
- `role`
- `content`
- `msg_type`
- `is_archived`
- `timestamp`
- 群聊相关作用域字段：`group_id` / `member_id`

#### `MemoryIndex`

长期记忆索引表，保存归档后的摘要与关联关系，当前关键字段包括：

- `index_id`
- `summary`
- `ref_uuids`
- `prev_index_id`
- `source_type`
- `user_id`
- `group_id`
- `member_id`
- `active_score`
- `created_at`

### 5.4 当前实现上的关键设计

1. **原始消息是唯一事实源**  
   长期记忆只是摘要索引，不替代原始消息。

2. **长期记忆可回溯原文**  
   通过 `ref_uuids` 指向原始消息。

3. **长期记忆带时间链**  
   通过 `prev_index_id` 串成时间线，支持“前情提要”式回忆。

4. **群聊作用域已进入索引层**  
   现在 `MemoryIndex` 也保存 `group_id/member_id`，便于群聊场景后续查询、筛选和维护。

## 6. 私聊主流程

### 6.1 私聊消息录入流程

#### 触发时机
用户发送私聊消息时。

#### 流程说明

1. AstrBot 收到私聊消息。
2. 插件识别消息是否为命令。
3. 若是普通消息，则调用记忆门面记录消息。
4. `MemoryManager` 将其写入 `RawMemory`。
5. 同时同步用户基础资料，用于画像系统补全。

#### 关键特征

- **只记录有效普通消息**
- **命令默认不写入记忆**
- **先存原文，后续再归档**
- **不阻塞主聊天过程**

### 6.2 私聊回复后写回流程

#### 触发时机
AstrBot 完成一次回复后。

#### 流程说明

1. 插件在 `after_message_sent` 阶段拿到最终回复内容。
2. 助手回复同样写入 `RawMemory`。
3. 更新用户画像中的互动统计信息。

#### 设计意义

这样数据库中保存的是 **完整双边对话闭环**，而不是只有用户发言。  
后续无论是归档、导出还是回溯，都会更接近真实聊天上下文。

### 6.3 私聊请求前记忆检索与注入

#### 触发时机
用户新发消息，AstrBot 即将请求 LLM 时。

#### 流程说明

1. 插件读取当前用户画像。
2. `IntentClassifier` 判断本次问题是否值得做长期记忆检索。
3. 如果需要检索，则调用 `retrieve_memories(user_id, query)`。
4. `MemoryManager` 执行召回、重排、回查原文。
5. 将画像块 + 记忆块注入到 prompt。
6. AstrBot 再发起正式 LLM 请求。

#### 为什么不是每次都检索

因为长期记忆检索有成本，如果每条消息都检索，会：

- 增加延迟
- 增加向量/数据库负载
- 注入过多无关上下文
- 抬高 token 成本

所以当前设计先做意图识别，再决定是否召回。

## 7. 长期记忆归档流程

### 7.1 归档不是实时发生

项目当前采用 **异步归档** 机制，而不是每来一条消息就立刻总结。  
归档由 `MemoryScheduler` 周期性触发。

### 7.2 归档触发条件

典型条件包括：

- 距最后一次有效消息超过配置的静默时间
- 未归档消息数达到最小阈值

私聊通常由：

- `private_memory_timeout`
- `min_msg_count`

控制。

群聊则优先使用：

- `group_memory_timeout`
- `group_min_msg_count`

若群聊专用项未配置，再回退到私聊阈值。

### 7.3 归档过程

1. 调度器扫描活跃会话。
2. 找到满足条件的未归档原始消息。
3. 按日期分组，避免一次总结过长。
4. 调用总结模型生成摘要。
5. 写入 `MemoryIndex`。
6. 将对应 `RawMemory` 标记为已归档。
7. 将摘要写入 Chroma 向量库。
8. 若向量写入失败，则走补偿/待重试路径。

### 7.4 归档后的结果

每次成功归档会得到一条长期记忆，具备：

- 摘要内容 `summary`
- 原文引用 `ref_uuids`
- 前置记忆 `prev_index_id`
- 来源类型 `source_type`
- 会话归属 `user_id/group_id/member_id`
- 创建时间 `created_at`

### 7.5 当前设计价值

- **低侵入**：不会拖慢实时聊天
- **节省 token**：只对成批消息做总结
- **保证可回溯**：长期记忆不是黑盒摘要
- **便于重建**：保留原始消息即可重新归档

## 8. 记忆折叠与时间线维护

### 8.1 为什么需要折叠

随着长期记忆数量增加，检索和管理会出现两个问题：

- 记忆碎片过多
- 多条相邻记忆描述的是同一时期的连续事件

因此项目中存在“折叠”机制，把若干总结进一步压缩为更高层叙事记忆。

### 8.2 当前折叠特征

折叠过程会：

- 选取已有长期记忆作为输入
- 生成更高层摘要
- 继承原始时间线关系
- 保留群聊作用域字段
- 写回新的 `MemoryIndex`

### 8.3 当前实现上的改进点

当前版本已经修复折叠过程中群聊作用域丢失的问题：  
折叠时会从源记忆中推导 `group_id/member_id` 并写入新的 `MemoryIndex`。

这意味着折叠后的群聊记忆不会失去归属范围，后续查询与管理更稳定。

## 9. 检索链路与降级策略

### 9.1 默认检索链路

长期记忆检索并不是“只查向量”或“只查数据库”，而是组合链路：

1. **向量召回候选**
2. **SQLite 回查索引**
3. **批量回查原始消息**
4. **基于时间、活跃度、相关性重排**
5. **拼装最终注入文本**

### 9.2 检索时的关键加权因素

当前系统会综合考虑：

- 语义相似度
- 时间新近性
- `active_score` 活跃度
- 意图分类

因此检索不是单纯“最像”优先，而是更偏向“当前最值得想起”。

### 9.3 当前降级路径

若 `chromadb` 不可用，或者向量链路失败，则自动降级到：

1. SQLite FTS5 BM25
2. 若仍不可用，再回退 LIKE contains

### 9.4 降级策略的意义

这保证了项目在以下环境下仍可工作：

- Python 3.13 下 Chroma 安装失败
- embedding provider 异常
- 向量维度不一致
- 本地依赖缺失

也就是说，**向量能力是增强项，不是可用性的硬依赖**。

## 10. 用户画像流程

### 10.1 画像的职责

画像系统不负责“记住某条原话”，而是负责抽取更稳定的用户信息，例如：

- 基础信息
- 职业
- 偏好/厌恶
- 性格倾向
- 关系状态
- 聊天统计

### 10.2 日常更新流程

1. 调度器每天检查哪些用户满足画像更新阈值。
2. 读取一段时间范围内的长期记忆。
3. 读取当前画像 JSON。
4. 把“当前画像 + 新长期记忆”喂给画像更新模型。
5. 输出 proposal。
6. 经过 `ProfileGuardian` 审核/修正。
7. 写入新画像前先做快照。
8. 更新 `_meta` 元信息与证据链。

### 10.3 画像元信息

当前画像系统支持记录证据链元数据，例如：

- `last_seen_at`
- `evidence_count`
- `evidence_refs`

这样做的价值是：

- 画像可解释
- 能追踪“为什么形成这个结论”
- 便于回滚与审计

### 10.4 回滚与衰减

当前画像系统还支持：

- **历史快照回滚**
- **偏好 TTL 衰减**

这可以避免两个问题：

1. 误更新导致画像污染
2. 很久以前的偏好永久占据画像

## 11. 群聊主流程

### 11.1 群聊系统的核心定位

群聊记忆不是私聊记忆的简单复制，而是一个 **隔离存储、按需启用、可配置归属边界** 的独立子系统。

### 11.2 群聊惰性初始化

群聊相关对象不会在插件启动时直接创建，而是在首次需要时通过 `_ensure_group_memory_manager()` 初始化。

初始化内容包括：

- 群聊 SQLite 数据库
- 群聊 `MemoryManager`
- 群聊命令处理器
- 群聊调度器
- 独立 Chroma 路径

### 11.3 群聊消息进入条件

群聊消息是否进入记忆系统，受以下配置控制：

- `enable_group_memory`
- `group_memory_only_friends`
- `group_memory_min_text_length`

因此群聊默认是更保守的采集策略，目的是降低噪声和隐私风险。

### 11.4 群聊归属模型

群聊链路引入了 `storage_id` 概念，表示一条群聊记忆最终归属给谁。

归属决策规则大致为：

1. 若 `group_memory_private_session_only = true`
   - 强制按发送者隔离
2. 否则读取 `group_memory_store_session_as`
   - `group_id`：按群归档
   - `user_id`：按人归档

### 11.5 三种常见群聊模式

#### 模式 A：按群聚合
适合记录群公共上下文，例如群梗、项目讨论、共同事件。

#### 模式 B：按人聚合
适合保留某个成员在群内的长期表达轨迹。

#### 模式 C：群聊私有化
即使消息发生在群里，也只给个人建账，隐私边界更强。

### 11.6 群聊请求前注入

在群聊请求前，系统会：

1. 检查群聊记忆是否启用
2. 检查白名单与最小字数
3. 解析 `storage_id`
4. 只检索本群或本人的群聊长期记忆
5. 可选附带私聊记忆（若启用 `group_memory_allow_private_recall`）

### 11.7 群聊回复后写回

群聊回复完成后，会把：

- 用户消息
- 助手回复

都写入群聊专属 `RawMemory`，为后续归档提供事实源。

## 13. 删除、撤销与恢复流程

### 13.1 删除能力

当前删除支持两类模式：

1. **只删除长期记忆索引**
2. **同时删除长期记忆和原始消息**

### 13.2 删除时的处理逻辑

删除长期记忆时，系统会：

- 找到对应 `MemoryIndex`
- 可选备份对应向量
- 将删除历史写入 SQLite
- 删除 Chroma 中对应向量
- 根据模式决定是否删除原始消息

### 13.3 撤销能力

项目支持 `/mem_undo` 和 `/group_mem_undo`。

撤销时会：

- 读取最近一次删除历史
- 恢复 `MemoryIndex`
- 恢复向量数据（若有备份）
- 必要时重新生成向量
- 恢复原始消息归档状态

### 13.4 当前设计价值

- 删除不是“一删就没”
- 撤销历史可跨重启保留
- 每个作用域保留最近 3 次删除记录
- 适合 WebUI 与命令误操作后的恢复

## 14. 数据导出流程

### 14.1 导出的事实源

导出不是从长期记忆导出，而是从 `RawMemory` 导出。  
这意味着导出数据更适合做审查、训练或迁移。

### 14.2 当前支持格式

- `jsonl`
- `json`
- `txt`
- `alpaca`
- `sharegpt`

### 14.3 导出用途

可用于：

- 人工审查对话质量
- 数据备份
- 模型微调数据构造
- 与其他训练工具链对接

### 14.4 导出文件位置

导出文件保存到：

- `exports/engram_export_{user_id}_{timestamp}.{format}`

## 15. WebUI 功能

WebUI 是本项目的管理后台，而不是核心运行必需项。

- 登录访问
- 首页统计
- 记忆浏览
- 记忆详情查看
- 记忆搜索
- 画像查看
- 群聊记忆管理
- 控制台基础管理

### 15.3 群聊 WebUI 当前特征

群聊记忆页面已支持：

- 默认展示全部群聊记忆

## 16. 配置如何影响整体行为

### 16.1 归档策略相关

以下配置直接影响“何时生成长期记忆”：

- `private_memory_timeout`
- `min_msg_count`
- `group_memory_timeout`
- `group_min_msg_count`
- 强制总结回溯天数限制
- 总结模型与总结提示词

### 16.2 画像策略相关

以下配置影响“何时、如何更新画像”：

- `min_persona_update_memories`
- 画像更新模型
- 并发限制
- 更新延迟
- `enable_profile_meta`
- `profile_history_limit`
- `profile_preference_ttl_days`
- `show_profile_evidence_in_image`

### 16.3 群聊边界相关

以下配置影响“群聊能否记录、按谁归属、是否联动私聊”：

- `enable_group_memory`
- `group_memory_only_friends`
- `group_memory_min_text_length`
- `group_memory_store_session_as`
- `group_memory_private_session_only`
- `group_memory_allow_private_recall`

### 16.4 检索降级相关

- `enable_sqlite_bm25_fallback`

它决定向量检索不可用时，是否优先进入 SQLite FTS5 BM25 召回路径。

### 16.5 WebUI 相关

- `webui_access_password`

用于控制 WebUI 登录访问。

## 17. 当前项目的关键设计原则总结

### 17.1 事实优先

项目始终以原始消息为事实源，长期记忆与画像都建立在其上，而不是直接覆盖原文。

### 17.2 异步优先

总结、画像更新、维护任务尽量放到后台调度器中执行，减少对主聊天链路的干扰。

### 17.3 分层抽象

系统不是只有“记忆”一个概念，而是分成：

- 原文事实
- 长期摘要
- 结构化画像

三层各司其职。

### 17.4 可回溯、可恢复

通过：

- `ref_uuids`
- `prev_index_id`
- 删除历史
- 画像快照

实现记忆与画像的可追踪、可恢复、可回滚。

### 17.5 可降级

向量检索失败时仍保留 SQLite 检索能力，保证插件基础可用性。

### 17.6 私聊与群聊边界明确

群聊不是简单混入私聊，而是：

- 独立数据库
- 独立向量目录
- 独立调度器
- 可配置归属边界
- 可控联动私聊

## 18. 当前版本能力边界

### 已明确具备

- 私聊长期记忆
- 群聊长期记忆
- 记忆检索与原文回溯
- 用户画像
- 删除/撤销
- 导出
- WebUI
- Chroma 不可用时的 SQLite 检索降级

### 当前边界特征

- 群聊默认关闭，需要明确启用
- 群聊画像并非独立画像体系，而是主要复用私聊画像
- 向量能力属于增强项，不是运行前提
- 画像更新是异步、批量、阈值驱动，而非每次即时更新

## 19. 一句话理解整个系统

`astrbot_plugin_engram` 当前本质上是一个围绕 **“原始对话 → 长期记忆 → 用户画像 → 请求前注入”** 构建的 AstrBot 长程记忆增强系统，并在此基础上扩展了 **群聊隔离、WebUI 管理、撤销恢复、导出训练数据与向量降级检索** 等工程化能力。
