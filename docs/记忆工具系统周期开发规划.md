# 记忆工具系统周期开发规划

## 1. 文档目标

本文档用于规划 `astrbot_plugin_engram` 记忆工具系统的后续优化周期。

当前系统已经具备长期记忆归档、向量检索、关键词兜底、工具检索和详情回溯能力，但仍需要从“工程可用”进一步提升到“稳定可控、可评估、可扩展、可治理”的阶段。

本文档重点覆盖：

- 每个开发周期要解决的问题
- 每项优化带来的收益
- 推荐实施顺序
- 可验收的完成标准

---

## 2. 当前阶段判断

当前记忆工具链路的优势是：

- 已有明确工具入口：`mem_search_tool` 与 `mem_get_detail_tool`
- 已有两段式工具设计：先搜索概览，再按 ID 查看详情
- 已有向量检索与 SQLite 关键词兜底
- 已考虑私聊、群聊、私聊回退等路由场景
- 已有一定回归测试基础

当前主要短板是：

- 显式工具调用仍可能被普通对话意图门控影响
- 工具返回内容偏 Markdown，可读但不够机器稳定
- 检索质量缺少离线评估集和量化指标
- 记忆系统内部职责仍分散在入口、工具处理器和管理器中

因此，后续开发应优先围绕 **稳定性、可预测性、评估能力、扩展能力** 展开。

---

## 3. 总体周期规划

| 周期 | 目标 | 核心收益 |
|---|---|---|
| P0：工具稳定化 | 修复显式工具调用、结构化输出、基础测试 | 让工具调用稳定可信 |
| P1：检索工程化 | 引入结果数据结构、搜索模式、多 ID 详情、更多元数据 | 让检索结果可扩展、可调试 |
| P2：评估闭环 | 建立召回评测集、指标、回归脚本 | 让检索调参从体感变成数据驱动 |
| P3：记忆治理 | Provider 抽象、生命周期拆分、文件化可读镜像 | 让系统具备长期演进能力 |
| P4：产品化增强 | 实体关系、事实失效、多源记忆接入 | 向 Mem0 / Zep / Letta 类系统靠齐 |

---

## 4. P0：工具稳定化周期

### 4.1 目标

让 LLM 明确调用记忆工具时，工具行为稳定、可预测，并且方便后续继续调用详情工具。

### 4.2 开发项

#### 4.2.1 显式工具调用绕过意图门控

当前问题：

- `mem_search_tool` 最终会走普通记忆检索链路。
- 如果意图分类器将 query 判定为 `skip`，即使 LLM 明确调用工具，也可能返回空结果。

优化方向：

- 工具调用 `retrieve_memories()` 时传入 `force_retrieve=True`。
- 将“普通对话是否自动检索”和“工具是否执行检索”分离。

收益：

- 提升工具调用可预测性。
- 避免“明明有记忆但工具说没有”的误判。
- 降低排查成本，明确工具调用一定会执行检索。

验收标准：

- 构造一个会被意图分类器判定为 `skip` 的 query。
- 直接调用 `mem_search_tool` 仍能执行检索。
- 自动注入链路仍保留原有 intent gate 行为。

---

#### 4.2.2 工具返回结构化结果

当前问题：

- 搜索结果是 Markdown 文本。
- LLM 可以阅读，但稳定提取 `memory_id`、来源、时间、分数时存在不确定性。

优化方向：

建议将每条记忆输出为稳定结构块，例如：

```xml
<memory id="abcd1234" source="private" created_at="2026-05-01 12:30" score="82">
摘要内容……
</memory>
```

或输出 JSON 风格结构：

```json
{
  "type": "memory_search_result",
  "query": "用户查询",
  "results": [
    {
      "memory_id": "abcd1234",
      "source_type": "private",
      "created_at": "2026-05-01 12:30:00",
      "score": 82,
      "summary": "摘要内容",
      "preview": "原文预览"
    }
  ]
}
```

收益：

- LLM 更容易稳定解析结果。
- 详情工具调用更可靠。
- 后续可以复用给 WebUI、测试脚本和评估脚本。
- 避免未来从 Markdown 反解析字段。

验收标准：

- 每条结果必须包含 `memory_id`、`source_type`、`created_at`、`score`、`summary`。
- LLM 提示中明确要求按 `memory_id` 调用详情工具。
- 旧格式兼容策略明确：直接替换或保留配置开关。

---

#### 4.2.3 收敛工具提示与实际工具集

当前问题：

- 代码中同时暴露 `mem_search_tool`、`mem_search_overview_tool`、`mem_search_detail_tool`。
- 后两个实际是兼容别名，可能增加模型选择混乱。

优化方向：

- 主推一个搜索工具：`mem_search_tool`。
- 主推一个详情工具：`mem_get_detail_tool`。
- 兼容别名可以暂时保留，但在工具描述中标记为兼容用途。
- 后续版本考虑移除或隐藏别名。

收益：

- 降低 LLM 工具选择成本。
- 减少维护重复逻辑。
- 让工具链路更接近“先搜概览，再取详情”的固定协议。

验收标准：

- 系统提示只推荐 `mem_search_tool` 与 `mem_get_detail_tool`。
- 兼容别名不再出现在主流程说明中。
- 测试确认别名行为仍与主工具一致，直到正式移除。

---

#### 4.2.4 补充 P0 回归测试

需要覆盖：

- 向量检索异常时回退 SQLite 关键词检索。
- 向量检索为空时回退 SQLite 关键词检索。
- 工具调用绕过 intent skip。
- 群聊记忆优先检索群聊库。
- 群聊允许私聊回退时可回退私聊库。
- 工具输出包含稳定 `memory_id` 字段。

收益：

- 防止核心工具链路反复回归。
- 后续重构 Provider 或结构化输出时有安全网。
- 明确“工具调用协议”本身也是受保护的产品能力。

验收标准：

- 新增或更新对应单元测试。
- 所有 P0 测试在本地通过。
- 失败时能明确定位是检索、路由还是格式问题。

---

## 5. P1：检索工程化周期

### 5.1 目标

把工具结果从“字符串拼接”升级为“内部数据结构 + 渲染层”，为后续搜索模式、评估和 UI 复用打基础。

### 5.2 开发项

#### 5.2.1 新增 MemorySearchResult 数据结构

建议字段：

```python
@dataclass
class MemorySearchResult:
    memory_id: str
    source_type: str
    created_at: datetime
    summary: str
    preview: str | None
    score: float | None
    confidence: str | None
    rank_reason: str | None
```

收益：

- 避免多层函数直接拼字符串。
- 检索逻辑、排序逻辑、展示逻辑解耦。
- 后续可以同时渲染 Markdown、JSON、XML、WebUI 卡片。

验收标准：

- `MemoryManager` 返回结构化结果或可转换对象。
- `MemoryToolHandler` 只负责工具输出渲染。
- 不再在检索核心逻辑中混入面向 LLM 的展示文案。

---

#### 5.2.2 支持搜索模式 mode

建议支持：

| mode | 行为 |
|---|---|
| `hybrid` | 默认模式，向量 + 关键词 + 时间 + 活跃度融合 |
| `semantic` | 更偏向向量语义召回 |
| `keyword` | 更偏向 SQLite FTS / 关键词召回 |
| `recent` | 更偏向最近记忆 |

收益：

- 不同问题可以选择不同检索策略。
- 方便调试“语义召回不好”还是“关键词召回不好”。
- 为评估不同策略提供入口。

验收标准：

- 工具参数新增 `mode`。
- 默认行为保持 `hybrid`。
- 不同 mode 有明确测试覆盖。

---

#### 5.2.3 详情工具支持多个 ID

当前问题：

- `mem_get_detail_tool` 一次只能传一个 ID。
- LLM 需要多轮调用才能比较多个候选记忆。

优化方向：

- 支持 `memory_ids: list[string]`。
- 保留单 ID 兼容。
- 限制一次最多返回 3-5 条详情，避免 token 过载。

收益：

- 减少多轮工具调用。
- 支持对多个候选记忆做交叉确认。
- 提升复杂问题的回答效率。

验收标准：

- 单 ID 调用保持兼容。
- 多 ID 调用按顺序返回多个详情块。
- 超过上限时明确截断并提示。

---

## 6. P2：评估闭环周期

### 6.1 目标

建立可重复运行的检索质量评估体系，让检索调参有数据依据。

### 6.2 开发项

#### 6.2.1 建立离线评估集

评估样例建议包含：

```json
{
  "query": "用户之前说过喜欢什么风格？",
  "expected_memory_ids": ["abcd1234"],
  "source_type": "private",
  "tags": ["preference", "profile"]
}
```

收益：

- 可以判断某次改动是否影响召回质量。
- 可以沉淀典型用户问题。
- 支持后续自动化回归。

验收标准：

- 至少包含偏好、事实、事件、时间范围、群聊、私聊回退等样例。
- 每个样例有明确目标记忆 ID 或目标摘要。
- 评估数据可在测试环境稳定重放。

---

#### 6.2.2 增加检索指标

建议指标：

| 指标 | 含义 |
|---|---|
| `recall@k` | 目标记忆是否出现在前 k 条 |
| `MRR` | 目标记忆排名越靠前分数越高 |
| `empty_rate` | 不该为空时返回空的比例 |
| `false_positive_rate` | 明显错误召回比例 |
| `avg_token_cost` | 平均工具输出 token 成本 |

收益：

- 排序权重调整有量化反馈。
- 可以发现“召回到了但排太后”的问题。
- 可以平衡召回质量与 token 成本。

验收标准：

- 提供本地评估脚本。
- 输出指标汇总。
- 后续排序参数变更前后可对比。

---

## 7. P3：记忆治理周期

### 7.1 目标

把记忆系统从具体实现中抽象出来，形成统一 Provider 生命周期，降低未来接入多后端和多形态记忆的成本。

### 7.2 开发项

#### 7.2.1 抽象 MemoryProvider 接口

建议接口：

```python
class MemoryProvider:
    async def prefetch(self, event, query): ...
    async def search(self, query, filters): ...
    async def get_detail(self, memory_id): ...
    async def build_context(self, memories): ...
    async def post_turn_sync(self, turn): ...
```

收益：

- 统一 SQLite、Chroma、文件记忆、外部记忆服务的生命周期。
- 减少 `main.py`、工具处理器、记忆管理器之间的职责混杂。
- 后续可插拔接入 Mem0、Zep 或自定义记忆后端。

验收标准：

- 当前 SQLite + Chroma 实现可作为默认 Provider。
- 工具层只依赖 Provider 接口。
- 自动注入链路和工具检索链路共享同一抽象。

---

#### 7.2.2 文件化可读镜像

优化方向：

- 数据库仍作为权威存储。
- 定期导出 `MEMORY.md` / `USER.md` 风格的人类可读镜像。
- 镜像用于审计、调试、人工修订建议，不直接替代数据库。

收益：

- 方便用户审计长期记忆。
- 方便排查“为什么模型记成这样”。
- 为未来多 Agent 共享记忆提供可读边界。

验收标准：

- 支持按用户导出可读镜像。
- 镜像中标明生成时间、来源、不可作为唯一事实源。
- 删除或撤销记忆后，镜像能重新生成并保持一致。

---

## 8. P4：产品化增强周期

### 8.1 目标

在稳定工具链和评估体系之上，引入更接近主流记忆系统的高级能力。

### 8.2 开发项

#### 8.2.1 实体与关系层

优化方向：

- 从长期记忆中抽取人物、地点、偏好、关系、事件。
- 记录事实之间的时间关系和置信度。
- 支持“某个事实是否已过期或被新事实覆盖”。

收益：

- 从“搜历史摘要”升级为“维护长期事实”。
- 更适合用户画像、关系记忆、长期偏好演化。
- 降低旧记忆与新事实冲突导致的回答错误。

验收标准：

- 支持最小实体类型：用户、偏好、事件、关系。
- 同一事实可被更新、覆盖或标记失效。
- 回答时优先使用较新且置信度更高的事实。

---

#### 8.2.2 多源记忆接入

可考虑接入：

- 本地 SQLite / Chroma
- Markdown 文件记忆
- 外部记忆服务
- 群聊共享记忆
- 用户私有核心画像

收益：

- 支持不同可信级别和生命周期的记忆。
- 让项目从单一插件记忆系统变成可扩展记忆平台。
- 更容易适配未来 AstrBot 生态或外部 Agent 系统。

验收标准：

- 每种记忆来源都有明确 `source_type` 与可信级别。
- 工具检索可按来源过滤。
- 不同来源的冲突处理策略明确。

---

## 9. 推荐实施顺序

建议不要一开始就做 Provider 大重构，而是按以下顺序推进：

1. **先做 P0**：修复工具调用可靠性、安全边界和结构化输出。
2. **再做 P1**：把结果对象化，避免后面继续堆字符串拼接。
3. **然后做 P2**：建立评估集，开始数据驱动调参。
4. **最后做 P3/P4**：在行为稳定后再抽象 Provider 和实体关系。

理由：

- P0 是用户可感知问题，收益最快。
- P1 是工程基础，能减少后续返工。
- P2 是质量保障，否则 P3/P4 改动越大越难判断是否退化。
- P3/P4 属于架构演进，适合在现有行为稳定后进行。

---

## 10. 阶段完成定义

### P0 完成定义

- 工具调用不会被 intent skip 误拦。
- 工具输出包含稳定 ID 和安全边界声明。
- 搜索工具与详情工具主路径清晰。
- 关键回归测试通过。

### P1 完成定义

- 内部有结构化搜索结果对象。
- 工具支持基础搜索模式。
- 详情工具支持有限多 ID 查询。
- 输出渲染与检索逻辑解耦。

### P2 完成定义

- 有可重复运行的检索评估集。
- 有 recall@k、MRR、空召回率等指标。
- 排序参数调整可通过评估报告对比。

### P3 完成定义

- 有最小可用 MemoryProvider 抽象。
- 当前 SQLite + Chroma 能通过 Provider 提供服务。
- 自动注入、工具搜索、详情回溯共用统一接口。

### P4 完成定义

- 支持实体、关系、事实更新或失效。
- 支持多来源记忆接入。
- 具备更接近产品化记忆系统的治理能力。

---

## 11. 总结

后续优化不应只追求“召回更多记忆”，而应优先保证：

- **稳定**：工具调用结果可预测。
- **安全**：历史记忆不能变成当前指令。
- **可评估**：检索质量能量化。
- **可扩展**：不同记忆后端能统一接入。
- **可治理**：记忆能审计、更新、失效和回滚。

因此，最推荐的近期开发路径是：

```text
P0 工具稳定化
→ P1 检索工程化
→ P2 评估闭环
→ P3 Provider 治理
→ P4 产品化增强
```

这条路径可以让项目从当前“实用型长期记忆插件”，逐步演进为更成熟的长期记忆系统。
